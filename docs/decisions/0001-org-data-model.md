# 0001. Модель даних відділів: один рядок членства з прапорцями, роль рахує база

- Статус: прийнято
- Дата: 2026-10-22
- AC: AC-ORG-02, AC-ORG-03, AC-ORG-04, AC-ORG-05, AC-ORG-11, AC-ORG-15, AC-ORG-19, AC-ORG-20, AC-ORG-24, AC-ORG-30,
  AC-ORG-33

## Контекст

Специфікація зрізу WS6 (`openspec/specs/department-setup/spec.md`, `employee-deactivation/spec.md`) вимагає:
схвалювачем і з автосхваленням можна бути лише заявником відділу (AC-ORG-02, AC-ORG-33); зняття заявника знімає
схвалення й автосхвалення (AC-ORG-03, AC-ORG-15); роль `approver` / `requester` визначає «Правило ролей» з
`requirements/product.md` (AC-ORG-04, 05, 19, 24), а `admin` від відділів не залежить (AC-ORG-11, AC-ORG-20);
деактивація нічого не змінює (AC-ORG-30). Застосунок працює без секретного ключа, тобто під RLS від імені користувача.

## Рішення

- Таблиця `department_members` з PK (`department_id`, `profile_id`): **рядок = членство заявника**, а `is_approver`
  і `auto_approve` — прапорці того самого рядка. Схвалювач без членства структурно неможливий; видалення рядка
  знімає все разом.
- Роль `approver` / `requester` зберігаємо в `profiles.role`, але **рахує її база**: тригер
  `private.on_department_members_change` → `private.sync_role` після кожної зміни членства. Роль `admin` тригер не
  чіпає. Та сама логіка — доменна функція `roleAfterChange` (`src/lib/org/roles.ts`) з юніт-тестами.
- Деактивація — лише `profiles.is_active = false`: членство, прапорці, дозволи й роль лишаються.

Міграція: `supabase/migrations/20261021213618_department_setup.sql`.

## Розглянуті варіанти

- Окремі таблиці `department_requesters` і `department_approvers` — ні: правило «схвалювач лише серед заявників»
  довелося б тримати тригером чи FK між таблицями, а зняття заявника — каскадом у кількох місцях.
- Роль, обчислена під час читання (view без колонки `role`) — ні: стартові політики й код шаблону вже читають
  `profiles.role`; тригер зберігає сумісність.
- Роль, яку ставить застосунок у server action — ні: прямий запит до Data API чи дві вкладки обійшли б правило.

## Наслідки

- Простіше: правила AC-ORG-02/03/15/33 тримає структура таблиці, а не код; ролі `requester` і `approver` узгоджені з членством, а `admin` залишається незалежною від відділів.
- Складніше: тригер і функції `security definer` треба рев'ювати уважно (кожна в `private`, `search_path = ''`,
  `revoke execute` від `public`, `anon`).
- Якщо PM додасть ролі, що не випливають із членства, правило в `private.sync_role` і `roleAfterChange` доведеться
  змінити новою міграцією й новим ADR.
