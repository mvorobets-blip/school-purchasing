# 0003. Хто робить запит — на сервері лише `getClaims()` + профіль, ніколи `getSession()`

- Статус: прийнято
- Дата: 2026-10-25
- AC: AC-FRM-02, AC-FRM-09, AC-APR-04, AC-ORG-12

## Контекст

Кожна сторінка порталу й кожна Server Action спершу з'ясовує, хто робить запит і з якою роллю: гість іде на вхід
(AC-FRM-09), користувач без прав отримує «Not enough permissions» (AC-FRM-02, AC-APR-04), деактивований не
входить (AC-ORG-12). Сесія Supabase живе в cookie, а cookie контролює браузер. `@supabase/supabase-js` дає три способи
дізнатися користувача: `getSession()`, `getUser()` і `getClaims()`. Документація Supabase прямо попереджає, що об'єкт
користувача з `getSession()` при зберіганні в cookie **не можна довіряти** — підпис токена не перевіряється. Правило
«ніколи `getSession()`» вже є в `AGENTS.md`, але поки його тримає лише рев'ю.

## Рішення

- На сервері (сторінки, Server Actions, `src/proxy.ts`) — лише `supabase.auth.getClaims()`: перевіряє підпис JWT
  (асиметричні ключі проєкту) і повертає `sub` — id користувача.
- Роль і активність — з таблиці `profiles` за цим id (RLS віддає профіль лише активному), ніколи з `user_metadata` чи
  claims токена. Одна точка входу — `getCurrentUser()` (`src/lib/org/current-user.ts`, `React.cache` на запит).
- `src/proxy.ts` лише оновлює сесію й перенаправляє гостя на `/login`; захист — у кожній сторінці й дії.
- `getSession()` у коді застосунку заборонено — ні виклику, ні посилання. Перевіряє CI.

## Розглянуті варіанти

- `getSession()` — ні: читає сесію з cookie без перевірки підпису; підроблений чи змінений cookie дав би чужу
  особу. Допустимий лише в браузері для показу, а такого коду в нас немає.
- `getUser()` на кожен запит — ні: безпечний (питає сервер Auth), але це мережевий запит на кожну сторінку й дію, а
  проєкт на безкоштовному тарифі; `getClaims()` перевіряє підпис локально з кешованими ключами.
- Роль у claims токена (custom access token hook) — ні: роль змінюється, коли адміністратор змінює відділи (ADR 0001),
  а токен живе до години — користувач діяв би зі старою роллю.

## Наслідки

- Простіше: одна функція визначає користувача; правило перевіряє машина, а не лише рев'ю.
- Складніше: `getClaims()` не бачить вихід з іншого пристрою, доки токен не сплив (до години). Для нас це прийнятно:
  деактивацію бачимо одразу, бо `profiles.is_active` читаємо на кожен запит, а RLS неактивному профіль не віддає.
- Якщо проєкт перейде на симетричний ключ JWT, `getClaims()` сам звертатиметься до сервера Auth — повільніше, але
  так само безпечно.

## Як перевіряємо

- CI: job «Авторизація лише через getClaims()» у `.github/workflows/architecture.yml` запускає
  `scripts/check-no-get-session.mjs` (`npm run check:auth`): будь-який `getSession` у `src/` поза коментарями — червоний
  прогін з файлом і рядком. Тести самого правила — `tests/scripts/check-no-get-session.test.ts`.
- Доказ, що правило ловить порушення: коміт `mutation: …` з `getSession()` → червоний прогін → revert (посилання в
  описі PR).
- Тести дій (`tests/purchase/*.test.ts`, `tests/org/*.test.ts`): без користувача дія повертає помилку й нічого не пише.
