# 0002. Подання й рішення щодо закупівлі — лише функціями бази, без прямого запису

- Статус: прийнято
- Дата: 2026-10-25
- AC: AC-FRM-02, AC-FRM-04, AC-FRM-06, AC-FRM-07, AC-FRM-08, AC-FRM-12, AC-FRM-13, AC-FRM-15, AC-APR-02,
  AC-APR-03, AC-APR-04, AC-APR-05, AC-APR-06, AC-APR-07

## Контекст

Зріз WS7 (`openspec/specs/purchase-form/spec.md`, `openspec/specs/approval-decision/spec.md`) додає два записи з
правилами прав: подання закупівлі (лише заявник відділу або адміністратор; власна закупівля — лише з дозволом;
щонайменше один рядок і всі поля рядка — AC-FRM-02, 04, 06, 15) і рішення схвалювача (лише схвалювач відділу заявки,
не власна заявка, лише зі статусу «Очікує схвалення», відхилення — з причиною — AC-APR-03 … 07). Заявка — це заголовок
і рядки, тобто кілька записів разом. Застосунок працює без секретного ключа, під RLS від імені користувача; у
supabase-js немає транзакцій (кожен запит — окрема транзакція). Будь-який вхід можна оминути: Server Action — публічний
POST, а Data API приймає запити з тим самим токеном напряму.

## Рішення

- Таблиці `purchase_requests` і `purchase_request_lines`: RLS, `revoke all … from anon, authenticated`, лише
  `grant select` для `authenticated` (політика: автор, схвалювач відділу, адміністратор). **Жодних** `insert`,
  `update`, `delete` для `authenticated` — статус, автора, відділ і рішення напряму не змінити.
- Запис — лише двома функціями в схемі `private` (`security definer`, `set search_path = ''`, `revoke execute` від
  `public`, `anon`): `private.submit_purchase(department, type, lines)` і
  `private.decide_purchase(request, decision, reason)`. Перші рядки кожної — перевірка прав (активний користувач, роль
  у відділі, дозвіл), далі правила AC, далі запис в одній транзакції. Помилка — `raise` з коротким текстом: права —
  код `42501` (`FORBIDDEN`, `OWN_REQUEST`), недопустиме значення — `22023` (`INVALID_TYPE`, `INVALID_DECISION`),
  правила форми й стану — `NO_LINES`, `INVALID_LINE`, `NO_REASON`, `NOT_PENDING`.
- Тонкі обгортки `public.submit_purchase` / `public.decide_purchase` (`security invoker`) з `grant execute` лише
  `authenticated` — їх викликає Server Action через `supabase.rpc(…)` і перетворює код помилки на повідомлення PM.
- Server Action теж перевіряє вхід (`getClaims()` + профіль — ADR 0003) і форму, але це зручність для повідомлень, а
  не захист: захист — у базі.

Міграції: `supabase/migrations/20261025184732_purchase_requests.sql` (задача 1),
`supabase/migrations/20261025192130_purchase_decisions.sql` (задача 3 плану `impl-purchase-approval`).

## Розглянуті варіанти

- Прямий `insert` / `update` з політиками RLS (`with check`) — ні: правило «щонайменше один рядок» і «всі поля
  рядка» охоплює кілька таблиць, а заголовок і рядки — окремі запити без транзакції (заявка без рядків лишилась би в
  базі). Для рішення довелося б дати `grant update (status, reject_reason, …)`, і схвалювач міг би змінити статус
  будь-якої заявки свого відділу в обхід правил «лише з pending» і «з причиною».
- Server Action з admin-клієнтом (секретний ключ) і перевірками в TypeScript — ні: обходить RLS, тож одна забута
  перевірка відкриває запис будь-кому; секретний ключ мав би бути на Vercel, а `AGENTS.md` і правило
  `check-server-boundary` цього не дозволяють.
- Окремий Route Handler (REST API) — ні: та сама проблема, що й з admin-клієнтом, плюс ще одна публічна точка входу
  без переваг над Server Action.

## Наслідки

- Простіше: правила прав живуть в одному місці — у функції, яку не оминути ні формою, ні Data API; заголовок і рядки
  записуються атомарно.
- Складніше: логіку в SQL важче читати й рев'ювати; кожна функція `security definer` — потенційна діра, тому
  `search_path = ''`, повні імена (`public.…`) і перевірка прав першими рядками обов'язкові.
- Повідомлення PM залежать від тексту `raise` — зміна тексту в міграції без зміни дії зламає повідомлення (ловлять
  тести дій).
- Новий запис (наприклад, рішення адміністратора за відділ без схвалювача, повернення на доопрацювання) — нова
  функція або нова версія функції новою міграцією, не `grant` на таблицю.

## Як перевіряємо

- Тести бази на PGlite (`tests/db/purchase.test.ts`, `tests/db/approval.test.ts`): справжні міграції, запити від
  імені ролей (`asUser`, `asAnon`). Для кожної відмови — помилка **і** незмінні дані; окремо — прямий `insert` в
  `purchase_requests` і прямий `update` статусу відхилено (немає `grant`).
- Мутаційна перевірка: прибрати перевірку з функції або додати `grant update` → тест червоний (таблиці в описах PR
  задач 1 і 3, щонайменше два червоні прогони CI).
